# 可视化 Agent 工作平台需求说明（初稿）

## 1. 文档目的与项目基线

本文件定义一个基于当前 Agent Framework 的本地可视化工作平台。用户应能从页面描述目标、查看或调整 Agent 任务图、校验并启动运行、跟踪每一步的状态与证据、处理需要人工决定的事项，并查看最终产物。平台是现有 Runtime 的交互层；执行事实、权限判断和状态转换仍由后端负责。

本文以仓库根目录的 `AI-Agent-Framework-Work-Orchestration.md` 和 Phase 1 实现为依据。**当前已实现**七个版本化 Schema、静态 DAG 校验、可信合同构造函数、状态转换及 CLI 示例；**尚未实现** Runs API、持久化、Scheduler/Worker、SSE、审批、Sandbox 和真实 Agent 执行。下文的“应支持”是建设目标，不表示功能已存在。

终端与 Web 的数据来源、连接方式、并发和断线恢复约束见 [终端与 Web 协同治理基线](terminal-web-sync-governance.md)。

### 目标用户与使用场景

首个版本面向单工作区内的框架使用者和开发者，典型任务是“分析登录异常，检索知识，生成最小修复建议，验证结果”。使用者需要知道：任务由哪个 Agent 承担、依赖谁、处于什么状态、用了哪些被允许的工具、为何失败或等待、结果有哪些可核对的证据。

平台优先支持桌面浏览器。本地部署是首个交付环境，不引入多租户或公开 Agent 市场。

## 2. 产品目标与验收口径

| 编号 | 目标 | 可观察的验收结果 |
| --- | --- | --- |
| G1 | 看得懂计划 | 同一页面展示目标、Task DAG、依赖、Agent、工具范围、预算与校验错误；可以定位具体问题节点。 |
| G2 | 控得住运行 | 有后端运行能力后，可创建、取消、查看 Run；页面动作只能通过后端 API 和状态机生效。 |
| G3 | 找得到原因 | 从 Run 可逐级打开 Task、事件、权限决定、验证结果、Checkpoint 和产物引用；失败有原因及下一步提示。 |
| G4 | 结果可核验 | `COMPLETED` 只在后端最终验收通过后显示；任务成功必须对应 Verifier PASS 和证据引用。 |
| G5 | 分阶段可交付 | Phase 1 可交付编辑与静态校验；后续随 Runtime 能力接入真实运行，不用伪造执行状态。 |

## 3. 范围与里程碑

| 阶段 | 平台交付范围 | 后端前置条件 |
| --- | --- | --- |
| P0：可视化计划工作台 | 导入示例或填写目标；画布展示 DAG；编辑草案节点与依赖；选择已注册 Agent/能力与工具子集；展示预算；调用现有校验逻辑并定位错误；保存/导出草案。页面明确标记“计划预览”，不提供假运行按钮。 | Phase 1 Schema、`PlanValidator`；需增加供页面使用的只读配置与计划校验接口，或先用本地适配层封装。 |
| P1：单 Agent 运行台 | 创建 Run、运行列表与详情、单 Task 状态和事件时间线、取消、最终结果。 | 蓝图 Phase 2：可信 Runs API、PostgreSQL、单 Agent Runtime、事件查询。 |
| P2：多 Agent 协作台 | 实时 DAG 状态、并行层、任务详情、结果与证据、Agent 版本、失败定位。 | 蓝图 Phase 3：多 Agent DAG 调度与结果聚合；SSE 或等效事件流。 |
| P3：可恢复与安全操作台 | Checkpoint、重试/恢复记录、审批及人工核对入口、Policy 决定、工具调用审计、Sandbox 产物。 | 蓝图 Phase 4–5 的持久恢复、Policy、Tool Gateway 与 Sandbox。 |

P0 的“保存/导出草案”可先使用 JSON 文件；运行历史与事件的权威存储须由后端提供。不要把浏览器本地数据当作 Run 的权威状态。

## 4. 核心用户流程

1. **建立目标**：输入目标、约束、验收条件和上下文引用，选择预设预算或在允许范围内调整。UI 显示可理解的验收名称，提交时映射到后端支持的稳定验收条件 ID。
2. **制定计划**：导入示例计划或使用画布添加 Task，设置名称、能力、Agent、依赖、优先级和可用工具子集；可查看 MainAgent 生成的草案并在提交前修改。未实现 MainAgent 时只提供手工/示例草案。
3. **校验计划**：显示环、缺失依赖、未注册 Agent、能力不匹配、预算超限、权限拒绝、并行写入冲突等问题；点击问题聚焦节点。校验通过才允许提交计划。
4. **启动并观察**：运行接口就绪后，由可信入口构建 `TaskContract` 并创建 Run；页面展示状态、并行层、当前任务、事件及预算使用量。
5. **处理异常**：可取消运行；需要审批或人工核对时展示原因、动作参数摘要、风险和审计记录，并按后端允许的动作处理。不可重试故障不能被页面直接改成成功。
6. **查看结果**：展示最终摘要、逐项验收结果、Task 证据、产物 URI/校验信息及 Trace；可从结果回到产生它的 Task 与事件。

## 5. 页面与交互需求

| 页面/区域 | 必须展示 | 用户可执行动作 |
| --- | --- | --- |
| 工作台首页 | 最近 Run、状态分布、待处理事项、快速进入示例 | 新建计划、打开 Run；P0 只显示草案入口。 |
| 计划编辑页 | 目标表单、DAG 画布、节点属性栏、Agent 清单、预算、校验面板 | 添加/删除草案节点、连线/断线、选择已注册 Agent 与工具子集、校验、保存/导出。 |
| 运行列表 | `run_id`、目标摘要、状态、创建/更新时间、计划版本 | 搜索、按状态筛选、分页、进入详情。 |
| Run 详情 | 状态与预算、DAG、当前活动 Task、事件时间线、最终结果 | 选中 Task、按事件定位节点、取消运行；按状态显示可用操作。 |
| Task 详情抽屉 | `task_id`、Agent/版本、能力、依赖、状态、尝试次数、有效工具、输入/输出引用、Verifier 结果、失败原因 | 跳转上游/下游 Task、打开证据或产物。 |
| 审批/核对视图 | 待处理动作、风险等级、Policy 原因、参数脱敏摘要、关联 `run_id/task_id/trace_id` | 仅在后端支持时批准/拒绝或记录人工核对结论；所有决定写入审计。 |

### DAG 画布规则

- 节点使用状态文字、图标与颜色共同表达状态，不仅靠颜色。边表示 `depends_on`，箭头从前置任务指向后续任务。
- 画布支持缩放、平移、自动布局、适应屏幕、按 Agent/状态筛选；节点可通过键盘列表视图访问。打开节点可查看完整字段。
- 编辑只作用于**草案计划**。运行启动后当前计划版本只读；若后续支持重规划，创建新 `plan_version` 并保留旧版本及已完成任务的轨迹。
- 不允许构造循环、悬挂依赖或重复 ID；允许先在草案中暂存无效状态，但提交/启动前必须通过后端校验。并行写同一工作区的冲突应定位到两个节点。
- 最多按现有 `Budget.max_tasks` 处理 128 个节点；超出预算时给出明确提示，不默默截断。

## 6. 功能需求与验收标准

### FR-01 目标与合同

- 前端采集 `goal`、`constraints[]`、`acceptance_criteria[]`、`context_refs[]` 和 `budget`。输入须按 Schema 做即时提示，最终以服务端验证为准。
- **权限不由用户输入表单声明**。前端可展示可信服务端计算出的权限上限和有效工具清单；不能把自然语言或导入 JSON 中的 `permissions` 当授权。
- 验收：含自授权限字段的外部请求被拒绝；合法请求可形成可追踪的 `run_id`。

### FR-02 Agent 与计划编辑

- Agent 列表来自受信 Registry，显示 `agent_id`、版本、能力、允许/禁止工具、风险上限。普通计划编辑者只能在服务端允许范围内选择，不能通过页面修改 Manifest 或扩大风险上限。
- 计划草案须包含 Task ID、目标、能力、Agent、依赖、优先级、工具子集、工作区引用以及输入引用；校验结果展示任务顺序、并行层、最大深度、有效工具和 Manifest 版本。
- 验收：对示例 `T1 → {T2,T3} → T4` 正确显示并行层；环、缺失依赖、能力/工具不匹配和写入冲突各能定位到节点。

### FR-03 运行状态与实时更新

- 运行详情按后端 `RunState` 和 `Task.status` 显示状态；事件依 `sequence` 排序，并提供时间、类型、Actor 和关联 Trace。状态更新可用 SSE；断线后先补取当前状态与缺失事件，再继续订阅。
- 显示 `budget_used` 的步骤数、模型调用数、工具调用数和耗时；成本估算仅在后端有可靠数据后加入。
- 验收：刷新页面和重连后状态与事件一致，不出现任务已失败而画布仍标成功；重复事件不重复插入时间线。

### FR-04 任务证据与结果

- `ResultEnvelope` 中摘要、证据、Verifier 检查项、产物引用和错误信息可从 Task 详情查看；敏感内容由服务端脱敏，页面不自行推断哪些秘密可以展示。
- 最终结果显示对合同验收条件的逐项结论及对应 Task/Artifact 链接。产物下载由后端授权并校验引用，页面不拼接任意本地文件路径。
- 验收：没有 Verifier PASS 的 Task 不能在页面呈现为已验证成功；从最终结论可追到证据和关联事件。

### FR-05 取消、审批与异常处理

- 取消须调用运行 API，并展示“请求中/已取消/取消失败”的服务端结果。终态 Run 不再显示可执行的取消动作。
- `WAITING_APPROVAL` 与 `WAITING_REVIEW` 要分开展示：前者等待策略允许的人为决定，后者需要核对不确定副作用。按钮及可选决定从后端返回，页面不自行推导可跳过的状态转移。
- 验收：重复点击不会产生重复决定；没有权限的用户不能执行操作；拒绝、批准及人工核对均关联事件与操作者。

## 7. 接口与数据约束

平台通过同源 HTTP API 与事件流访问 Runtime，不直接连接 PostgreSQL、Redis、MinIO 或 Worker。接口应使用现有 Schema 的 `schema_version`、稳定 ID 和 UTC 时间；更改字段要有兼容策略。建议接口清单如下，其中仅 CLI 校验在当前代码中可用：

| 接口能力 | 建议路径或形式 | 依赖阶段 |
| --- | --- | --- |
| 可用 Agent、能力、工具和验收条件 | `GET /catalog` | P0 新增 |
| 静态计划预检 | `POST /plans/validate`，返回结构化问题及 `PlanReport` | P0 新增，封装 `PlanValidator` |
| 创建 Run | `POST /runs`，服务端构建可信 `TaskContract` | P1，蓝图 Phase 2 |
| 查询 Run、Task、Event | `GET /runs/{id}`、`GET /runs/{id}/tasks`、`GET /runs/{id}/events` | P1，蓝图 Phase 2 |
| 一致的页面快照 | `GET /runs/{id}/view`，返回状态及 `event_cursor` | P1–P2 新增 |
| 运行列表与事件流 | `GET /runs`、`GET /runs/{id}/events/stream?after=...`（SSE） | P1–P2 新增/完善 |
| 取消 | `POST /runs/{id}/cancel` | P1，蓝图 Phase 2 |
| 产物、审批、恢复记录 | 由 P3 设计明确的只读与操作端点 | P3，蓝图 Phase 4–5 |

所有写操作须有身份校验、服务端授权、幂等处理及审计。请求失败返回稳定错误码、可读说明和相关字段/节点 ID；前端保留用户草案，便于修正后重试。P0 的计划预检可以直接校验受信服务端授予的权限上下文，不能让浏览器伪造该上下文。

## 8. 非功能需求

| 方面 | 要求 |
| --- | --- |
| 一致性 | PostgreSQL 是运行状态和事件的权威来源；前端缓存仅用于展示。事件断流或乱序时重新同步，不能凭本地倒计时推进状态。 |
| 安全 | 仅展示授权工作区的数据；秘密、令牌、原始敏感日志和工具参数应在服务端脱敏。L3 操作默认不可用；真实外部写入在后端安全边界完成前不开放。 |
| 可用性 | 本地环境下，128 节点以内的静态 DAG 打开和基本交互应保持流畅；事件流断开时有醒目提示与手动重试入口。具体性能阈值在首个可运行版本实测后固定。 |
| 可访问性 | 表单有标签与错误说明；核心流程可用键盘完成；状态同时用文字、图标和颜色表达。 |
| 可维护性 | 前端字段类型由版本化 API/Schema 约束；记录页面版本和后端 Schema 版本，避免静默解析失败。 |
| 部署 | 优先支持本地开发与 Docker Compose 环境；前端与 API 的地址、认证及 SSE 代理配置有示例。 |

## 9. 不纳入首版的能力

多租户、Agent Marketplace、任意递归 Agent、任意外部工具接入、真实生产外部写入、拖拽编辑正在执行的计划、浏览器直接修改任务状态、完整 Event Sourcing 和大规模分布式监控不在首版范围。聊天式生成计划可作为后续入口，但仍必须经过同一 Validator 和可信权限入口。

## 10. 首个可开发切片与交付清单

建议先完成 **P0 可视化计划工作台**，用当前仓库的 `examples/contract.json`、`examples/plan.json`、`examples/manifests.json` 和 `examples/environment.json` 作为验收样例。交付包括：

1. 页面信息架构与低保真线框：目标表单、DAG 画布、节点抽屉、校验面板。
2. `GET /catalog` 与 `POST /plans/validate` 的请求/响应约定及实现；校验逻辑复用当前 `PlanValidator`。
3. 可编辑草案、导入/导出、示例计划加载、结构化错误定位。
4. 端到端演示：加载示例 → 查看并行层 → 制造循环或权限冲突 → 看到定位错误 → 修正后校验通过。

进入 P1 前需确认后端 Runs API 与持久化已通过蓝图 Phase 2 验收。进入 P2/P3 时再增加真实执行、实时状态与人工处理按钮，避免视觉稿先于运行语义定型。
